# Peritus — Full System Overhaul Plan

> **Core Value:** "Build a grounded AI expert on any topic in minutes."
>
> The real differentiator is the build pipeline, not the chat. Unlike a generic RAG chatbot, Peritus
> pulls from 5+ authoritative source types, has Claude validate every source, builds a property graph
> over the validated content, and generates a named expert persona grounded in that specific graph.
> The promise: an AI tutor that only knows what it was taught, from sources you can see, with citations
> you can trace.

## 1. What We Are Building

**From:** An MCP server (FastMCP + FastAPI) that lets AI agents search a personal book library.

**To:** A local CLI tool (`peritus`) that builds grounded, credentialed AI subject-matter experts from
multi-source corpora. The user runs one command. Sources are fetched automatically from 5+ provider
types, Claude validates and scores each one, a property graph is built over the validated content,
and a named expert persona is generated — ready to answer questions with full citations and traceable
sources.

### Design Principles

- **Fully automatic build** — no user approval gate. Claude is the curator; the credential card is
  the receipt.
- **Credentials, not configuration** — transparency is delivered after the build through a verifiable
  record of every source, quality score, and dropped source.
- **Property graph, not a vector blob** — nodes carry typed metadata (concept, claim, difficulty,
  argument structure); edges carry typed relationships (supports, contradicts, builds_on). This is
  the structural differentiator from a generic RAG store.
- **Persona grounded in corpus** — the expert persona is generated by Claude after ingestion, based
  on what sources were actually collected. It reflects the corpus, not a prompt the user wrote.
- **Single-user, local, no auth** — a personal CLI tool. No Supabase JWT, no user_id scoping,
  no FastAPI, no MCP.

## 7. Database Schema

```sql
-- ── experts ──────────────────────────────────────────────────────────────────

CREATE TABLE experts (
    id              SERIAL PRIMARY KEY,
    name            TEXT NOT NULL UNIQUE,   -- user-facing slug, e.g. "stoic philosophy"
    topic           TEXT NOT NULL,          -- raw build topic string
    persona_name    TEXT,                   -- e.g. "Dr. Aletheia Stoikos"
    persona_bio     TEXT,                   -- paragraph bio
    persona_style   TEXT,                   -- full system prompt instruction block
    status          VARCHAR(20) NOT NULL DEFAULT 'building',
                                            -- building | ready | failed
    source_count    INTEGER NOT NULL DEFAULT 0,
    chunk_count     INTEGER NOT NULL DEFAULT 0,
    node_count      INTEGER NOT NULL DEFAULT 0,
    edge_count      INTEGER NOT NULL DEFAULT 0,
    avg_quality     REAL,
    error           TEXT,                   -- populated on status='failed'
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- ── sources ───────────────────────────────────────────────────────────────────
-- All discovered sources are stored — passed AND dropped.
-- Dropped sources appear in the credential card under "DROPPED".

CREATE TABLE sources (
    id              SERIAL PRIMARY KEY,
    expert_id       INTEGER NOT NULL REFERENCES experts(id) ON DELETE CASCADE,
    source_type     VARCHAR(20) NOT NULL,   -- wikipedia|arxiv|youtube|exa|web
    url             TEXT,
    title           TEXT NOT NULL,
    author          TEXT,
    quality_score   REAL,                   -- 0–10, Claude-assigned
    relevance_score REAL,                   -- 0–10, Claude-assigned
    content_type    VARCHAR(50),            -- textbook|paper|tutorial|reference|opinion
    difficulty      INTEGER,               -- 1–5
    key_claims      JSONB,                 -- string[] extracted by Claude
    passed          BOOLEAN NOT NULL,      -- false = dropped, still logged
    drop_reason     TEXT,                  -- populated when passed=false
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX ON sources (expert_id, passed);

-- ── source_chunks ─────────────────────────────────────────────────────────────

CREATE TABLE source_chunks (
    id              SERIAL PRIMARY KEY,
    expert_id       INTEGER NOT NULL REFERENCES experts(id) ON DELETE CASCADE,
    source_id       INTEGER NOT NULL REFERENCES sources(id) ON DELETE CASCADE,
    sequence_n      INTEGER NOT NULL,
    text            TEXT NOT NULL,
    context_text    TEXT,                  -- contextualizer enrichment
    embedding       vector(3072),
    chunk_meta      JSONB,                 -- e.g. {section, page, timestamp}
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX ON source_chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON source_chunks USING gin (to_tsvector('english', text));
CREATE INDEX ON source_chunks (expert_id);
CREATE INDEX ON source_chunks (source_id);

-- ── property graph ────────────────────────────────────────────────────────────

CREATE TABLE expert_nodes (
    id          SERIAL PRIMARY KEY,
    expert_id   INTEGER NOT NULL REFERENCES experts(id) ON DELETE CASCADE,
    node_type   VARCHAR(20) NOT NULL,      -- concept | claim
    label       TEXT NOT NULL,             -- short canonical name
    description TEXT,
    properties  JSONB,
        -- {
        --   "difficulty": 1-5,
        --   "content_type": "definition|theorem|example|argument|counterargument",
        --   "confidence": 0.0-1.0,          (for claims)
        --   "argument_structure": {...}      (premises[], conclusion)
        -- }
    chunk_ids   INTEGER[],                 -- source_chunks this node was derived from
    embedding   vector(3072)               -- optional, for concept similarity search
);

CREATE INDEX ON expert_nodes (expert_id, node_type);

CREATE TABLE expert_edges (
    id              SERIAL PRIMARY KEY,
    expert_id       INTEGER NOT NULL REFERENCES experts(id) ON DELETE CASCADE,
    from_node_id    INTEGER NOT NULL REFERENCES expert_nodes(id) ON DELETE CASCADE,
    to_node_id      INTEGER NOT NULL REFERENCES expert_nodes(id) ON DELETE CASCADE,
    edge_type       VARCHAR(30) NOT NULL,
        -- supports | contradicts | builds_on | defines | exemplifies | cites
    weight          REAL NOT NULL DEFAULT 1.0,
    properties      JSONB
);

CREATE INDEX ON expert_edges (expert_id);
CREATE INDEX ON expert_edges (from_node_id);
CREATE INDEX ON expert_edges (to_node_id);
```

Migrations live in `migrations/` following the existing `001_initial.sql` numbering convention.
The full migration drop-and-recreate script for Peritus will be `migrations/005_peritus.sql`.

## 8. Source Fetchers

Each fetcher implements the `Fetcher` protocol:

```python
@dataclass
class RawSource:
    source_type: SourceType
    url: str
    title: str
    author: str | None
    text: str           # full raw text, no truncation
    metadata: dict      # source-specific extras (e.g. arxiv_id, video_id)

class Fetcher(Protocol):
    async def fetch(self, topic: str, max_results: int = 5) -> list[RawSource]: ...
```

| Fetcher | Method | Default max |
|---|---|---|
| `WikipediaFetcher` | REST API — search then fetch full article wikitext | 4 |
| `ArxivFetcher` | `arxiv` package — full-text PDF abstract + body | 3 |
| `YoutubeFetcher` | Exa discovers video URLs; `youtube-transcript-api` fetches transcripts | 5 |
| `ExaFetcher` | `exa-py` neural search — returns full page text via contents API | 8 |
| `WebFetcher` | `httpx` fetch + `BeautifulSoup` main-content extraction | 4 |

`--depth deep` doubles each fetcher's `max_results`.
`--sources arxiv,exa` restricts to only those fetchers.

All fetchers run concurrently via `asyncio.gather`. A fetcher failure is logged and skipped —
it does not abort the build.

## 9. Claude Validation Contract

One Claude call per raw source. Batched with a concurrency limit of 5 to avoid rate limits.

**Input:** topic string + source title + first 2,000 characters of text.

**Output (JSON):**

```json
{
  "quality_score": 8.5,
  "relevance_score": 9.1,
  "content_type": "reference",
  "difficulty": 2,
  "key_claims": [
    "Virtue is the only true good",
    "External events are indifferent to flourishing"
  ],
  "drop_reason": null
}
```

**Drop condition:** `quality_score < 5 OR relevance_score < 5`

When dropped, `drop_reason` is populated with a short phrase (`"off-topic"`, `"low quality"`,
`"too brief"`, `"opinion without substance"`). The source row is written to the DB with
`passed = false` and the drop reason. It will appear in the credential card under DROPPED —
this is the accountability mechanism.

## 10. Property Graph Design

### Why a graph over a plain vector store

A generic RAG stores `(chunk_text, embedding)`. Retrieval returns the closest chunks, but
the agent has no structural context: it does not know whether two chunks support or contradict
each other, which concepts are foundational to others, or what the argument structure of a
claim is.

The Peritus graph adds that structure. After chunking, a second Claude pass reads batches of
10 chunks and extracts:

**Nodes** (`concept` or `claim`):
```
concept: "Dichotomy of Control"
  difficulty: 2
  content_type: definition
  description: "Epictetus's distinction between what is in our power (prohairesis) and what is not"
  chunk_ids: [14, 17, 23]

claim: "Virtue is sufficient for happiness"
  content_type: argument
  confidence: 0.9
  argument_structure:
    premises: ["External goods are indifferent", "Only virtue is in our control"]
    conclusion: "Virtue alone is sufficient for eudaimonia"
  chunk_ids: [8, 12]
```

**Edges** (typed relationships):
```
"Dichotomy of Control"  --builds_on-->   "Virtue Ethics"
"Virtue Ethics"         --defines-->     "Eudaimonia"
"Marcus Aurelius"       --exemplifies--> "Dichotomy of Control"
"Kant's Autonomy"       --contradicts--> "Stoic Acceptance"
"Meditations Book IV"   --supports-->    "Amor Fati"
```

### How graph retrieval enriches chat

1. Semantic search returns `chunk_id: 17`
2. `graph/retriever.py` looks up nodes whose `chunk_ids` include 17 → finds "Dichotomy of Control"
3. Traverses edges one hop: `builds_on` → also pulls "Virtue Ethics" node + its chunks
4. Traverses `contradicts` → surfaces the Kant tension for the agent to address
5. Agent receives: raw chunk text + related concept descriptions + relationship annotations

This context allows the agent to give a structurally grounded answer, not just a chunk collage.

## 11. Persona Generation Contract

Triggered once all ingestion + graph extraction is complete.

**Input to Claude:**
- Expert topic
- Summary of every passed source (title, content_type, key_claims, quality_score)
- Top 20 concept nodes by connectivity degree

**Output:**

```json
{
  "name": "Dr. Aletheia Stoikos",
  "bio": "A classicist and practising Stoic who has spent 30 years studying the primary texts...",
  "style": "You are Dr. Aletheia Stoikos, a specialist in Stoic philosophy. Respond with precision and warmth. Ground every claim in the texts you have studied. Prefer the primary sources — Epictetus, Marcus Aurelius, Seneca — over secondary commentary. When sources disagree, surface the tension explicitly rather than papering over it. Do not speculate beyond what your sources support. Always cite the work and section when quoting or paraphrasing."
}
```

The `style` field is stored as `experts.persona_style` and injected as the system prompt prefix
into every chat turn. The persona name and bio appear in the credential card header.

## 12. Chat Agent Flow

```python
# chat/agent.py

async def respond(
    expert: Expert,
    question: str,
    history: list[Turn],
) -> Answer:
    # 1. Plan — decompose question into 2–4 retrieval subqueries
    subqueries = await plan(question, expert.topic)

    # 2. Parallel hybrid search across all subqueries
    chunks = await batch_search(
        subqueries,
        expert_id=expert.id,
        top_k=10,           # per subquery; deduped + reranked after merge
    )

    # 3. Graph expansion — enrich each hit with concept neighbor context
    enriched = await graph_retriever.expand(chunks, expert_id=expert.id)
    # Each hit now carries:
    #   .text            — original chunk text
    #   .citation        — "Title, Section — SourceType · Q:8.4"
    #   .related_concepts — list of neighboring node labels + descriptions
    #   .relationships   — typed edges touching this chunk's nodes

    # 4. Coverage assessment — one gap-fill pass if needed
    coverage = await assess_coverage(question, enriched)
    if not coverage.satisfied:
        extra = await batch_search(
            coverage.suggested_queries,
            expert_id=expert.id,
            top_k=5,
        )
        enriched += await graph_retriever.expand(extra, expert_id=expert.id)

    # 5. Respond in persona with inline citations
    return await anthropic_client.respond(
        system=expert.persona_style,
        question=question,
        context=enriched,
        history=history,
    )
```

**Chat display (rich):**
- Answer rendered with inline citations: `[Meditations, Book IV — Wikipedia · Q:9.1]`
- Collapsible "Sources used this turn" panel
- Graph context callout when a `contradicts` edge was traversed: "Note: this conflicts with..."

## Key Decisions Log

| Decision | Rationale |
|---|---|
| **Fully automatic build, no approval gate** | Removes friction; credentials card delivers the same transparency after the fact, not during |
| **Dropped sources logged, not silently discarded** | The credential card must be a complete audit trail; showing what was rejected and why is part of the trust model |
| **Postgres for graph storage (not Neo4j)** | JSONB + FK joins are sufficient at this scale; keeps infrastructure to one service alongside pgvector |
| **Typer over Click** | Better type inference from annotations; matches the dataclass-heavy style already in the codebase |
| **Persona generated from corpus, not user prompt** | Expert reflects what was actually collected; grounded, not generic |
| **Single-user, local, no auth** | CLI is a personal tool; eliminating auth removes an entire layer of complexity |
| **text-embedding-3-large retained** | Proven in existing codebase; changing model requires migration + re-embed of all chunks |
| **Property graph via Claude extraction, not NLP pipeline** | Claude understands semantic relationships at topic level far better than dependency parsers or NER alone |
