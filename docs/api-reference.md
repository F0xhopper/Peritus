# API reference

Every HTTP endpoint the FastAPI server exposes, grouped by router. The server is the single
authority: the web app, the Rust TUI and the Python CLI are all clients of it.

An interactive, always-current version is generated by FastAPI itself at **`/docs`** (Swagger) and
**`/redoc`**, with the OpenAPI schema at **`/openapi.json`**. This page is the orientation; that is
the contract.

- Base URL in development: `http://localhost:8000`
- Base URL in production: `https://peritus.fly.dev`

## Authentication

Peritus uses [Supabase Auth](https://supabase.com/docs/guides/auth): email one-time code or Google
SSO. The API is a **backend-for-frontend** — it holds the Supabase anon key and proxies the sign-in
calls, so clients only ever handle the resulting session tokens.

Authenticated requests carry the access token:

```
Authorization: Bearer <access_token>
```

Access tokens are verified locally against the project's JWKS endpoint (asymmetric ES256/RS256
signing keys, the current Supabase default), falling back to the legacy HS256 shared secret if that
is all the project has. See `api/src/peritus/api/auth.py`.

**Open dev mode.** With `SUPABASE_URL` unset the server requires no login and every request acts as
`BOOTSTRAP_ADMIN_EMAIL`. Setting `PERITUS_ENV=production` makes the server *refuse to start* in
that state, so a missing setting can never silently drop production into admin mode.

**Ownership.** Every expert is scoped to the user who built it. An expert the caller cannot read
returns **404, not 403** — existence is never disclosed. Mutation (rebuild, delete, curate) is
owner-only at every layer regardless of visibility.

**A legacy static key** (`PERITUS_API_KEY_HASH` with `Authorization: Bearer <key>`) is still
accepted as a fallback credential. Supabase login is the recommended path.

## Conventions

**Errors** are uniform JSON carrying the request id, which is also on the `X-Request-ID` response
header:

```json
{ "detail": "…", "request_id": "01JB…" }
```

Quote the request id when reporting a 500 — the message is generic on purpose; the id is what makes
it actionable.

**Build denials are structured 402s** the client switches on rather than parses:

```json
{ "error": { "code": "insufficient_credits", "message": "…", "required": 3, "balance": 1 } }
```

Codes: `insufficient_credits`, `tier_not_in_plan`. Each carries a renderable remedy — see
[catalog-and-credits.md](catalog-and-credits.md).

**`null` is not zero.** Any count the system did not record comes back as `null` with a reason.
Clients must render that as a gap, never coerce it to `0`.

**Rate limits.** The unauthenticated auth endpoints (`/auth/otp`, `/auth/verify`,
`/auth/password/*`, `/auth/signup`, `/auth/resend`, the OAuth pair) and the account steps that
send email are throttled per IP (`AUTH_RATE_LIMIT` /
`AUTH_RATE_WINDOW`, default 10 per 60s). Both chat endpoints are throttled per user
(`CHAT_RATE_LIMIT` / `CHAT_RATE_WINDOW`, default 20 per 60s) — chat is free to the user but not to
the operator.

**Streaming.** Build progress and chat responses are `text/event-stream`. See
[Server-sent events](#server-sent-events) below.

## Auth — `/auth`

Public: these endpoints *are* the login flow.

| Method | Path | Description |
|---|---|---|
| `GET` | `/auth/status` | Whether this server requires login |
| `POST` | `/auth/otp` | Send an email one-time code |
| `POST` | `/auth/verify` | Exchange a code for a session. `type`: `email` (sign-in) or `signup` (confirm a new account) |
| `POST` | `/auth/password/login` | Sign in with email and password. 403 `email_not_confirmed` resends the confirmation code |
| `POST` | `/auth/signup` | Create a password account. 202 `{confirmation_required}`, the same for an existing email |
| `POST` | `/auth/resend` | Resend the sign-up confirmation code. Always 204 |
| `POST` | `/auth/password/forgot` | Email a password-reset code. Always 204 |
| `POST` | `/auth/password/reset` | Reset code + new password → a session; other sessions revoked |
| `GET` | `/auth/oauth/authorize` | Begin the Google SSO (PKCE) flow |
| `POST` | `/auth/oauth/exchange` | Exchange an OAuth code for a session |
| `POST` | `/auth/refresh` | Rotate a refresh token for a new session |
| `POST` | `/auth/logout` | Revoke sessions server-side. `?scope=global` (default), `local` or `others` |
| `GET` | `/auth/me` | The current authenticated user |

Sign-out revokes server-side, so a leaked refresh token cannot be replayed.

**No endpoint here says whether an email has an account.** Sign-up, resend and forgot-password
answer the same for a stranger as for a member, and a wrong password reads the same as an unknown
email. Errors the client branches on carry `detail: {code, message}`.

## Account — `/auth/account`

The signed-in caller's own account. Sessions and deletion read the Supabase `auth` schema
directly and answer 503 on a database without it (local development).

| Method | Path | Description |
|---|---|---|
| `GET` | `/auth/account` | Profile, identities, `has_password`, pending `new_email` |
| `PATCH` | `/auth/account` | Set the display name |
| `DELETE` | `/auth/account` | Delete the account and everything it owns. Body `{confirm_email}`; refused for the operator |
| `POST` | `/auth/account/password` | Set or change the password. Changing needs `current_password`; 409 `reauthentication_needed` emails a code to resubmit as `nonce`. Signs other sessions out |
| `POST` | `/auth/account/reauthenticate` | Email that code again |
| `POST` | `/auth/account/email` | Start an email change; a code goes to the new address |
| `POST` | `/auth/account/email/verify` | Enter a change code → `{complete, session}` |
| `GET` | `/auth/account/identities/authorize` | PKCE URL that links Google to this account |
| `DELETE` | `/auth/account/identities/{id}` | Unlink a sign-in method (never the last) |
| `GET` | `/auth/account/sessions` | Signed-in devices; `current` marks the caller's |
| `DELETE` | `/auth/account/sessions/{id}` | Sign one other device out |

## Experts

| Method | Path | Description |
|---|---|---|
| `GET` | `/experts` | List the caller's experts |
| `POST` | `/experts/build` | Build an expert. **SSE** stream of build events |
| `GET` | `/experts/{slug}` | Expert detail: persona, key concepts, counts, source-type breakdown, readiness, access |
| `DELETE` | `/experts/{slug}` | Delete an expert, cancelling any in-flight build |
| `PATCH` | `/experts/{slug}/catalog` | Curate catalog placement (admin) |
| `PUT` | `/experts/{slug}/avatar` | Set the stored avatar recipe |
| `GET` | `/experts/{slug}/picture` | The expert's found picture |
| `POST` | `/experts/{slug}/picture/refresh` | Search Wikimedia again for a picture |
| `DELETE` | `/experts/{slug}/picture` | Remove the found picture |

`POST /experts/build` takes `{"topic": "..."}` and nothing else is required. The server derives the
slug, resolves the deepest tier the caller's plan and balance afford, takes an idempotent credit
hold (keyed by job id, so a double-submit charges once), enqueues a durable job, and returns an SSE
tail of the event log.

### Build lifecycle

| Method | Path | Description |
|---|---|---|
| `GET` | `/experts/{slug}/build/events?after=N` | Reconnect to a build from a cursor. **SSE** |
| `GET` | `/experts/{slug}/build/status` | Point-in-time build job status |
| `GET` | `/experts/{slug}/build/usage` | Metered token and dollar cost for the build |
| `POST` | `/experts/{slug}/build/cancel` | Cancel the active build (hold refunded in full) |

Builds are durable. Disconnecting changes nothing; reconnect with `after=<last seq>` and the server
replays from that cursor, then continues live.

## Chat and conversations

| Method | Path | Description |
|---|---|---|
| `POST` | `/experts/{slug}/chat` | Ask a one-shot question. **SSE** stream of tokens + citations |
| `POST` | `/experts/{slug}/conversations` | Start a persisted conversation |
| `GET` | `/experts/{slug}/conversations` | Conversations for one expert |
| `GET` | `/conversations` | All the caller's conversations |
| `GET` | `/conversations/{id}` | One conversation with its messages |
| `PATCH` | `/conversations/{id}` | Rename a conversation |
| `DELETE` | `/conversations/{id}` | Delete a conversation |
| `POST` | `/conversations/{id}/messages` | Send a message. **SSE** stream of tokens + citations |

Chat is free and ungated over anything the caller can read, including the public catalog — the
build already paid for the corpus. A conversation holds a **stream claim** so two clients cannot
stream the same turn; an interrupted stream releases it.

## The evidence record

Read-only. Full contract in [audit-api.md](audit-api.md).

| Method | Path | Description |
|---|---|---|
| `GET` | `/experts/{slug}/corpus-report` | Every source considered — kept *and* rejected — with scores, rubric version, drop reason and the search that produced it |
| `GET` | `/experts/{slug}/corpus-report/export` | The same as CSV, RIS or BibTeX (`?format=`) |

| `GET` | `/experts/{slug}/contradictions` | Where sources in this corpus were judged to disagree, resolved to passages |
| `GET` | `/experts/{slug}/graph` | The concept graph: claims, concepts and their edges |
| `GET` | `/experts/{slug}/answer-audits` | The retrieval trail behind every answer |
| `GET` | `/experts/{slug}/answer-audits/{id}` | One trail in full: subqueries, coverage verdict, every passage considered |

`computed: false` on contradictions means *not analysed yet* — never "no contradictions found".

## Server-sent events

Three endpoints stream: `POST /experts/build`, `GET /experts/{slug}/build/events`, and the two chat
endpoints.

**Build events** are an append-only log with monotonic `id:` cursors. Two rules clients get wrong:

1. **A closed stream is not a finished build.** Only `done`, `error` or `cancelled` is terminal.
   Anything else — a proxy timeout, a sleeping laptop, a deploy — means reconnect with
   `?after=<last seq>`.
2. **`stage_degraded` is not a failure.** Graph extraction and persona are enrichment. Their
   failure leaves a working, answerable expert; only corpus assembly can fail a build.

**Chat events** stream answer tokens followed by structured `{n, label}` citations. `[n]` markers
are parsed against the passage list server-side; a marker pointing at no passage is stripped from
the prose and flagged, never rendered as a real citation. Only passages the answer actually cited
count as its sources.

## Readiness, not status

An expert becomes answerable at readiness `chat_ready`, a full stage before its build job reaches
`done`. **Gate the chat affordance on `readiness`, never on `status`** — reading `status` hides a
working expert for the length of graph extraction.

| Readiness | Means |
|---|---|
| `pending` | Enqueued or assembling its corpus |
| `chat_ready` | Corpus embedded — answers with citations |
| `graph_ready` | Concept graph extracted and resolved |
